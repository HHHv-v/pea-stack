## 2026-11-22 (v7 출시 → v14)

### 1. 짧게 연타만 해도 50층까지 올라가는 버그

**증상**
- v7을 출시한 뒤 친구들이 "화면을 그냥 연속으로 누르기만 해도 50층까지 간다"고 알려 줌.
- 폭을 맞추지 않고 탁탁 두드리기만 해도 게임이 잘 끝나지 않고, "딱!"과 콤보까지 나옴.

**원인**
- 짧게 탁 누르면 막대는 처음 폭 12px에서 조금만 자라서 약 20px 폭으로 놓여요.
- 실수하면 새 폭은 `아래층 폭 − 틀린 폭 × 벌칙 배수`예요. 벌칙 배수가 1보다 작아서, 연타할수록 탑 폭이 막대 폭(약 20px)에 점점 가까워져요(수렴).
- 그런데 게임 오버 기준이 **16px**이라 탑이 20px 근처에 머무는 동안 게임이 끝나지 않았어요.
- 탑 폭과 막대 폭이 비슷해지면 오히려 **"딱!" 판정이 터지고**, 2번 연속 딱부터는 콤보로 폭이 10px씩 **회복**됐어요.
- 정리하면 "좁아짐 → 딱 → 회복 → 다시 좁아짐"이 반복되면서 연타만으로 수십 층을 올라갔어요. 이게 50층까지 가던 진짜 이유예요.

```ts
// v7: 기준이 연타 막대 폭(약 20px)보다 작았음
if (nw < 16) gameOver();
```

**해결**
- 게임 오버 기준을 `max(36px, 시작 폭 × 15%)`로 올렸어요(`TUNING.minWidthPx`, `TUNING.minWidthRatio`).
- 탑이 연타 막대 폭까지 좁아지기 전에 게임이 끝나서, "딱!"이 터지는 구간에 들어갈 수 없어요.
- 콤보만 따로 막는 코드는 넣지 않았어요. 기준 하나로 콤보 문제도 같이 사라져요.

```ts
// v14
if (nw < Math.max(TUNING.minWidthPx, this.baseW * TUNING.minWidthRatio)) gameOver();
```

**확인 (시뮬레이션, 각 1,000판)**

판정·벌칙·속도·무작위 계산을 게임과 똑같이 따라 하는 스크립트로, 매번 같은 길이로 연타했을 때를 비교했어요.

| 연타 1번 길이 | v7(16px): 평균 층 / 판당 딱 | v14(36px): 평균 층 / 판당 딱 |
|---|---|---|
| 0.04초 | 108층 / 46.5번 | 7층 / 0번 |
| 0.06초 | 73층 / 27.3번 | 8층 / 0번 |
| 0.08초 | 54층 / 17.8번 | 8.6층 / 0번 |
| 0.1초 | 42층 / 12.3번 | 9.5층 / 0.01번 |
| 0.15초 | 30층 / 6.4번 | 21층 / 4.5번 |

**남은 약점과 다음 대응**
- 0.15초쯤 조금 길게 톡톡 누르면 막대가 40px 안팎이 돼서, 좁아진 탑과 우연히 맞는 경우가 있어요(평균 21층).
- 실제 테스트에서도 쉽게 뚫리면 둘 중 하나로 대응해요.
  - 폭이 좁을 때(예: 60px 이하)는 "딱!" 판정을 주지 않기 (추천)
  - 게임 오버 기준을 50px로 올리기

### 2. "너무 쉽다"는 반응 → 판정 비율 계단식으로 변경

**증상**
- v7 출시 후 "다들 너무 쉽다"는 반응이 나옴.
- v7은 판정 비율이 ±11%에서 140층에 걸쳐 ±4%로 아주 천천히 줄어서, 초중반이 넉넉했어요.

**해결**
- 판정 비율을 직선 대신 **20층마다 계단식**으로 줄이고, 바닥값을 정했어요(`perfectRatio()` 함수).

| 층 | 0~19 | 20~39 | 40~59 | 60~79 | 80~99 | 100~119 | 120~ |
|---|---|---|---|---|---|---|---|
| 판정 비율 | ±9% | ±7.5% | ±6% | ±5% | ±4% | ±3% | **±2% (고정)** |

- 0~59층은 20층마다 1.5%p, 60층부터는 20층마다 1%p씩 줄이고, 2%에서 더 줄이지 않아요.
- 막대 속도: `115 + 층 × 1.2`(최대 280) → `140 + 층 × 1.6`(최대 320).

- 그래도 "아직 쉽다"는 피드백 → **콤보 가속** 추가. 연속 딱 1번마다 막대 속도 +8%, 최대 +100%예요. 층과 상관없이 붙고, 실수하면 바로 원래 속도로 돌아와요(`TUNING.comboSpeedUp`, `comboSpeedMax`). 잘 맞출수록 빨라져서, 초반에 딱만 이어 가며 쉽게 올라가는 걸 막아요.
- 직접 해 보니 **빨라지는 느낌이 안 났어요.** 원인은 막대마다 곱하던 0.75~1.35배 무작위 속도였어요. 판마다 ±30%씩 흔들리니 +8%씩 오르는 변화가 묻혔어요. → 처음엔 **무작위를 없앴는데**, 아래 4번 문제가 생겨서 되돌렸어요. "딱!" 아래에 `속도 ×1.24`처럼 배수를 표시하는 것도 넣어 봤지만, 화면이 복잡해서 뺐어요.
- 콤보 가속 최대치는 +50% → **2배**(13콤보)로 올렸어요. 3배도 검토했지만, 100층 이상에서 막대가 한 프레임(1/60초)에 15px씩 움직여 허용 폭(±5~7px)을 건너뛸 수 있어서 2배로 정했어요.

- 그래도 "전체적으로 너무 쉽다" → **콤보 폭 회복 제거**. 원래 2번 연속 딱부터 딱마다 폭이 10px씩 넓어져서, 실수로 좁아진 탑을 콤보로 쉽게 되살릴 수 있었어요. 이제 한 번 좁아진 폭은 돌아오지 않아요(`recoverAfter`, `recoverPx` 삭제).

```ts
export function perfectRatio(n: number) {
  if (n < 60) return 0.09 - 0.015 * Math.floor(n / 20);
  return Math.max(0.02, 0.06 - 0.01 * (Math.floor((n - 60) / 20) + 1));
}
```

### 3. 어려워진 만큼 막대가 자랐다 줄었다 왕복하게 변경

**배경**
- 판정이 빡빡해져서, 한 번 지나치면 바로 실수가 되는 게 너무 가혹해졌어요.
- v7은 아래층의 1.9배까지 누르고 있으면 그 자리에서 자동으로 놓였어요.

**해결**
- 누르는 동안 막대가 아래층의 **1.7배**(`TUNING.swingMax`)까지 자랐다가 다시 줄고, 처음 폭(12px)까지 줄면 또 자라요. 자동으로 놓이지 않아요.
- 끝에 닿은 프레임에 넘친 만큼은 반대 방향으로 되돌려서, 프레임 간격이 커도 범위를 넘지 않게 했어요.
- 손가락 입력이 취소되면(`cancelHold`) 폭과 함께 방향(`dir`)도 처음으로 되돌려요.

```ts
cur.w += cur.dir * cur.speed * dt;
if (cur.w >= maxW) { cur.w = maxW - (cur.w - maxW); cur.dir = -1; }
else if (cur.w <= 12) { cur.w = 12 + (12 - cur.w); cur.dir = 1; }
```

**확인**
- 웹 빌드를 자동화 브라우저로 열고 3.2초 동안 누른 채 0.4초마다 화면을 찍었어요. 막대가 1.7배까지 자랐다가 다시 줄어드는 것을 확인했어요.
- 손을 떼면 정상적으로 쌓였어요.

### 4. 무작위 속도를 없애자 '같은 길이로 누르기'만으로 끝없이 올라감

**증상**
- 2번 항목에서 콤보 가속을 체감하게 하려고 막대 속도의 무작위(0.75~1.35배)를 없앴어요.
- 시뮬레이션해 보니 **매번 같은 길이로 누르기만 해도** 게임이 끝나지 않거나 90층 가까이 올라갔어요.

**원인**
- 속도가 층과 콤보로만 정해지니, 같은 시간 동안 누르면 항상 같은 폭의 막대가 나와요.
- 1번 연타 버그와 같은 원리로, 탑 폭이 그 막대 폭에 맞춰지면 "딱!"이 계속 터지고 콤보로 폭이 회복돼요.
- 결국 무작위는 '보고 맞춰야 하는 게임'을 만드는 핵심 장치였어요.

**해결**
1. 무작위 속도(0.75~1.35배)를 **다시 넣었어요**. 콤보 가속은 그 위에 곱해요: `층별 속도 × 콤보 배수 × 무작위`.
2. 탑 폭이 시작 폭의 **25%(약 57px)보다 좁으면 "딱!"을 주지 않아요**(`TUNING.noPerfectBelowRatio`). 좁아진 탑에서 연타로 콤보를 쌓는 길을 막아요.
3. 콤보 가속이 무작위에 묻히는 건 감수했어요. 평균으로는 콤보가 쌓일수록 확실히 빨라져요(배수 표시는 넣었다가 뺌).

**확인 (시뮬레이션, 각 1,000판, 같은 길이로 계속 누름)**
| 누르는 길이 | 무작위 없음 | 무작위 + 좁은 탑 딱 금지 (최종) |
|---|---|---|
| 0.04~0.12초 | 7~10층 | 7~10층, 딱 0번 |
| 0.15초 | **끝나지 않음** | 평균 15층 (최대 22) |
| 0.35초 | 87층 | 평균 22층 (최대 49) |
| 0.45초 | 92층 | 평균 20층 (최대 41) |

### 5. 앱인토스 검토 반려: 원스토어 AI 게임 등급 사용 불가

**증상**
- 앱인토스 콘솔 반려 사유: "운영 중인 스토어 링크를 업로드 해주세요. 원스토어 AI 게임은 앱인토스에서 출시할 수 없는 점 양해 부탁드려요."
- 원스토어 웹게임(AI를 활용한 게임으로 등록)의 등급분류 ONIA-SG-261117-0003으로 신청했었어요.

**원인**
- 앱인토스는 원스토어 'AI 게임'으로 받은 등급을 인정하지 않아요(공식 문서에도 명시).
- 원스토어에서 안드로이드 APK로 다시 내는 방법은, 'AI를 활용한 게임 여부'에 사실대로 "예"라고 답하면 안드로이드 등록이 막혀서 쓸 수 없었어요.

**해결**
- 같은 게임을 **PWA로 만들어 Microsoft Store에 출시**했어요(`npm run build:pwa`, `/pea-stack/pwa/`).
- IARC 등급을 가져와서 GRAC 자체등급분류 **MSFT-SG-261117-0096**(전체이용가)이 조회되는 것을 확인했어요.
- 콘솔 등급분류 정보를 바꿨어요.
  - 스토어 링크: https://apps.microsoft.com/detail/9MZGWWNL2SWT
  - 자체등급분류사업자명: Microsoft Corporation
  - 등급분류번호: MSFT-SG-261117-0096
  - 자체등급분류 게임물 화면: Microsoft Store 스크린샷 2장
- 재검토 요청 후 **통과해서 v7 출시**.

**참고**
- 난이도나 판정 수치만 바꾸는 업데이트는 화면이 그대로라서 등급분류를 다시 받지 않아도 돼요.
- Microsoft Store 앱은 PWA 주소를 감싼 패키지라서, gh-pages의 `pwa/`를 다시 배포하면 스토어 버전도 같이 바뀌어요.
